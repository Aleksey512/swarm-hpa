# GitOps deploy failed on relative configs:/secrets: paths (temp compose written to /tmp)

**Date:** 2026-07-06 14:11
**Files:** internal/adapter/stackdeploy/deploy.go, internal/app/gitopsync/loop.go, internal/core/port/gitops.go
**Severity:** high

## Problem

A GitOps deploy of a stack whose compose file references file-backed configs or
secrets via relative paths (e.g. `configs/nginx.conf`, resolved relative to the
compose file) failed with:

```
stackdeploy: deploy "nginx": open /tmp/configs/nginx.conf: no such file or directory
```

The referenced file actually lived in the repo worktree at
`repos/<repo>/configs/nginx.conf`, but `docker stack deploy` looked for it under
`/tmp` and could not find it. So any stack using relative file paths for
configs/secrets was undeployable through the daemon.

## Root Cause

`stackdeploy.writeTempCompose` wrote the carry-forward-adjusted compose to the OS
temp dir via `os.CreateTemp("", ...)` — i.e. somewhere under `/tmp`, inside the
container. The path of this temp file is what the deployer hands to
`docker stack deploy`.

`docker stack deploy` resolves a compose's relative `configs:`/`secrets:` `file:`
entries **relative to the directory of the compose file it is given**. Because the
temp file was in `/tmp`, every relative path got resolved under `/tmp` — where the
real files do not exist (they are in the repo worktree). The bug was not in the
path math of `docker stack deploy`; it was in WHERE we wrote the temp compose. We
discarded the original file's directory information entirely when we serialized to
a fresh map and wrote it to `/tmp`.

Why this went unnoticed: every existing deploy test serializes an in-memory
compose map and asserts only on the parsed content / replica carry-forward — none
of them have relative `configs:`/`secrets:` `file:` entries, so none exercised
path resolution against the temp file's location.

## Solution

Write the temp compose **next to the original compose file**, so relative paths
resolve against the same directory they resolve against for the source file — the
repo worktree. The worktree directory of the original compose is already
reconstructable in the loop (`filepath.Join(WorktreePath, filepath.Dir(ComposeFile))`),
both of which the loop already uses for sops discovery/decrypt and config rotation.

The directory is threaded through the deploy port as a new optional
`DeployOpts.ComposeDir` field (kept in `core/port` so the core owns the contract,
per the ports-and-adapters layering). The adapter's `writeTempCompose` now takes a
`dir` argument and passes it to `os.CreateTemp(dir, ...)`. An empty `ComposeDir`
falls back to the OS temp dir, preserving the historical behavior for tests and
any caller that does not care about relative paths.

## Prevention

- **Temp files that participate in relative-path resolution must be co-located
  with their source.** When you materialize a derived/temp version of a file that
  another tool will resolve relative paths against, write it in the source's
  directory — not in `/tmp`. `/tmp` is fine for opaque blobs; it is wrong for
  anything that carries relative path semantics.
- **When a port carries context the adapter needs, put it on the opts struct
  rather than reaching out for it.** The adapter deliberately does not know the
  worktree path; the loop does. `DeployOpts` is the correct channel.
- **Cover the location, not just the content.** Deploy tests asserted only on the
  parsed compose map. Add an assertion on WHERE the temp file was written whenever
  relative-path resolution is in play.
- **Follow the relative-path trail during review.** Any `os.CreateTemp("", ...)`
  whose output is later consumed by an external tool that resolves paths is a
  smell — ask "what does that tool resolve paths against?"
